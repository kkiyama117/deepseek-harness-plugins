# 振り返りと開発手順の改善

作業を終えるとき、または開発手順の具体的な詰まりを改善するときに読む。入力は実際の結果と観測した負担。問題がなければ改善Issueや新しい手順を無理に作らない。

## やること

1. 再調査、待ち時間、引き継ぎの不足、手戻りのうち重要なものを短く振り返る。
2. 具体的な再発や大きな負担があれば、既存Issueへ証拠を追加するか、一つの検証可能な改善仮説として起票する。投稿する場合は [課題整理](02-intake.md)に従う。
3. 変更先は原因に合わせて選ぶ。説明不足なら必要時に読む資料、反復作業ならコマンド、工程の不足ならスキル、守る必要のある実行制限なら実行基盤。すべてを常時読み込む指示へ追加しない。
4. 一度に変える要因を絞り、次の実案件で使う。要求の達成と回帰防止は必須条件とし、改善対象の工程の再調査・修正指示・待ち時間・費用を必要な範囲で比較する。
5. 案件やモデルが違う時間を単純比較せず、測っていない値や生産性向上を捏造しない。総合点だけでなく、以前は通っていた個別ケースが失敗するようになっていないかも確認する。

担当・セッション・レビューの分け方を見直す場合は [設計の参考資料](../references/project-setup.md#設計の参考資料)を参照する。参考記事の観測値をこの環境の効果や保証として扱わない。

## この工程の結果と次の作業

変更不要、改善仮説、採用・修正・撤回の判断を、観測した根拠とともに残す。手順の整備完了と効果検証完了は別であり、効果が未確認ならIssueの残条件または関連する追跡Issueに対象案件・確認項目を残す。

改善の実装も今回の依頼に含まれるなら [完了条件と計画](03-plan.md)へ戻る。将来の案件や新しい改善Issueの存在だけで、自動着手の許可とはしない。

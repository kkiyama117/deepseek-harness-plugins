# 実装・検証・レビュー

変更、検証、レビュー指摘への修正に入るときに読む。入力は [計画](03-plan.md)で決めた完了条件・設計・編集範囲・検証方法。既存の結果がある場合はその続きから進める。

## 実装と検証

1. 変更を小さく戻せる単位に分け、完了条件と関係のない修正を混ぜない。
2. 繰り返す決定論的な操作は既存コマンドを優先し、必要ならプロジェクトの規約に沿ってスクリプト化する。
3. 実効モデル、費用・時間・試行上限が重要な処理は、対応する実行基盤の制御を使う。対応していない制限を「保証」と呼ばない。
4. 対象プロジェクトで必要な検証を選んで実行する。完了条件ごとに、対象の版・成果物、実行した確認、観測結果、証拠の所在を対応付ける。agentの成功報告だけではなく、成果物や動作を確認する。

## 必要なレビューと修正

独立レビューは変更の影響とプロジェクト規約に応じて行い、些細な変更にも別agentを必須にしない。認証・権限・データ消失などの高リスク変更は、その危険に対応する確認を加える。

独立レビューには受入条件、対象差分、必要な設計理由、検証結果を渡す。修正は原則として実装した担当が行い、重要な指摘は再現テストや独立した再確認で解消を確かめる。主担当の「修正済み」という報告だけで閉じず、再確認は指摘箇所と影響範囲に絞る。複数モデルによる二重レビューを一律には要求しない。

## 失敗・変更・中断

検証失敗は原因を調べてから修正する。効果のない再試行を続けない。繰り返し処理には開始前に有限の試行上限を決め、上限到達時は残る問題を報告する。失敗に依存する反映は止め、完了条件を下げたり、期待値を書き換えて成功に見せたりしない。

調査で範囲や設計の見直しが必要になったら [計画](03-plan.md)へ戻る。中断時は [中断と再開](../references/project-setup.md#中断と再開)に沿って状態を残す。

## この工程の結果と次の作業

変更した成果物と、各完了条件の検証結果・証拠・未確認事項を揃える。必要な確認を通過したら [反映と結果報告](05-deliver.md)へ進む。通過しない場合は未完了として、失敗の証拠と具体的な残作業を返す。

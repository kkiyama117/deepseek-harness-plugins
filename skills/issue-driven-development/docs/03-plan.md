# 完了条件と進め方

課題の調査・設計・実装を始める前、または範囲や受入条件を見直すときに読む。入力は元の依頼、既存Issueや調査結果、確認済みの作業先と権限。

## 完了条件と担当を揃える

着手記録はIssueコメントや既存の作業計画に短く残し、既に記載済みなら不足分だけ補う。

- 目的、対象・対象外、観測可能な完了条件とその確認方法。
- 担当する人またはagent、変更するリポジトリ・ファイル範囲・作業ブランチ。
- 調査・実装・投稿・反映のうち今回認められている範囲。
- 必要な実行予算・時間上限、未解決事項と依存先。

担当の記録は排他ロックではない。既存担当と作業中のブランチを確認し、同じファイルを複数の担当が同時に編集しない。共有作業にはworktree等を使い、他の未コミット変更を取り込まない。

| 種類 | 着手時に揃えるもの | 主な確認 |
|---|---|---|
| bugfix | 再現手順、期待値と実測値、影響する版・環境 | 可能なら修正前の失敗と修正後の成功、周辺の回帰 |
| 機能追加 | 利用例、受入条件、対象外、必要な設計判断 | 利用者の操作経路、既存機能への影響 |
| 開発手順の改善 | 具体的な詰まり、現状の手順、一つの改善仮説 | 手順が実行可能か、次の開発で詰まりが減ったか |

再現不能なら調査結果と不足条件を示し、未検証の修正で解決済みにしない。大きな不確実性は調査タスクとして切り出し、その完了と元の要望の完了を区別する。

## 文脈を保って分ける

原則として一つの機能・不具合は同じ主担当が調査・設計・実装・テスト・修正を続ける。工程名だけで担当やセッションを分けず、内部タスクは既存Issueや作業計画のチェックリストで管理する。独立した目的・完了条件を持つ課題は分けてよい。PRはセッション数に合わせず、独立して検証・取り消しできる単位で分ける。

委任は、必要な文脈を切り離せる調査・検証、または接続仕様と編集範囲が明確な独立実装に有効な場合に選ぶ。テストコマンドの実行だけなら主担当がツールを使う。

委任や複数モデルが有効な場合だけ [orchestrate-agents](https://github.com/kkiyama117/deepseek-harness-plugins/blob/main/skills/orchestrate-agents/SKILL.md)を読む。同スキルは実行構成とモデル経路、本スキルは課題から反映・改善までを担当する。利用できない環境ではそのハーネスの手段を使い、未実装の互換性を主張しない。

## この工程の結果と次の作業

完了条件、必要な設計判断、担当・編集範囲、確認方法が揃った単位から [実装・検証・レビュー](04-implement-verify.md)へ進む。設計だけの依頼なら設計を返し、例示した作業を実行しない。

中断やコンテキスト更新が必要なら [中断と再開](../references/project-setup.md#中断と再開)を読み、引き継ぎを残す。同じ主担当で続ける方針は、無制限に履歴を保持する指示ではない。

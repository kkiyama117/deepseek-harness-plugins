# 課題の登録・整理

困りごとをIssueにする、既存Issueを補う、重複や管理先を判断するときに読む。作業先と権限が不明なら先に [作業先の確認](01-scope.md)を行う。

## やること

1. 起票前に、対象リポジトリのopen/closed Issueと関連PRを検索する。解決済みなら修正の適用状況を調べ、再発なら既存Issueとの関係を示す。
2. 同じ課題なら既存Issueへ新しい証拠を追記する。別の原因や独立した完了条件を持つ課題は関連リンクを付けて分ける。
3. そのプロジェクト固有の問題は元のリポジトリに置く。複数プロジェクトで使う手順・スキル・道具の改善は、その共通資産の管理先に置く。共通改善の入口は [deepseek-harness-plugins Issues](https://github.com/kkiyama117/deepseek-harness-plugins/issues)。相互リンクは必要な場合だけ付け、同じ作業を二重管理しない。
4. 人間の短い報告を受け付ける。AIは観測した事実、期待する結果、再現条件または利用例、影響範囲を補い、不明点は不明と書く。原因の仮説を事実として書かない。
5. 起票者の問題記述を保ち、調査の補足はコメントへ追記する。本文の訂正が必要な場合も元の意味を変えず、変更理由を残す。
6. 公開前に本文と添付を確認する。秘密、個人情報、非公開プロジェクト名、内部URL、私的な会話や生ログを転載しない。公開できない証拠は権限のある保存先に残し、公開Issueには必要最小限の説明を置く。投稿する場合は [GitHubでの操作](../references/project-setup.md#githubでの操作)を読む。

起票のためだけに無関係な軽微事項を収集しない。ユーザーが起票を求めていない些細な修正は、既存の作業範囲内で扱えるなら新規Issueを必須にしない。

## この工程の結果と次の作業

対象Issueと補った事実、または公開可能な下書きを返す。GitHubに書けない場合は投稿済みと報告しない。重複なら関連先と判断理由を残し、同じ課題を二重に実装しない。

実装や調査を続ける依頼なら [完了条件と計画](03-plan.md)へ進む。起票のみの依頼なら投稿または下書きの結果を返し、実装へ勝手に進まない。

# Flash / Astra 比較Flow

## 目的と既存Flowとの関係

同じ固定入力と受入条件で、`flash`（Flash単独）、`astra`（Astra単独）、`flash-advisor`（Flash実行＋必要時のみAstra相談）を比較する。モデルの回答と、独立した合否判定・実測費用は別に記録する。

既存の`coordinator-advisor`は「設計→バッチ調整→必要時相談→ワーカー→統合→レビュー→設計者による受入」を行う。今回の第三方式には余分な段階が多いため、同じグラフ実行基盤で軽量な`executor-advisor`テンプレートを使用する。独自のモデルルーターや別のアプリケーションは追加しない。

```text
comparison（指定順に実行。方式間の回答は渡さない）
  flash:         Flash実行 ───────────────────→ 回答
  astra:         Astra実行 ───────────────────→ 回答
  flash-advisor: Flash実行 ── done ───────────→ 回答
                         └─ needs_advice → Astra相談 → Flash継続 → 回答
                         └─ blocked ──────────────────────────→ 失敗記録
```

相談なしなら全体3呼び出し、相談ありなら最大5呼び出し。相談は1回までで、続行するFlashは新しい子Sessionに試行と助言の記録を渡す方式。同じSessionの再開ではない。相談後も完了できなければ失敗として残す。追加レビューやモデルによる勝者判定は自動では行わない。

## 入力とコンパイル

`examples/comparison.json`は合成データの動作確認用であり、性能評価用の課題ではない。実課題の入力はskill外に保存する。`task`には共通の目的・固定された資料・受入条件・制約を記載する。`fixtureId`は資料の版を識別する値（実験ではハッシュ等）、`order`は3方式を一度ずつ含む配列とする。fixtureId自体は資料の同一性を検証しない。

`examples/comparison-policy.json`は現在一覧に登録されているモデル経路を設定した例。実行前に経路と実効モデルを再確認する。実行ツールはreasoning effort指定をサポートしないので、Astraの実効設定も記録する。

```sh
node bin/compile.mjs examples/comparison.json examples/comparison-policy.json /ABSOLUTE/PRIVATE/new-comparison
```

既存コンパイラが入力を検証して`tool-input.json`等を生成する。親ディレクトリは事前に存在する必要がある。コンパイルはモデルを呼ばない。実行は`references/run-dsh.md`に従って生成した入力をそのままDSHの`workflow`へ渡す。

## 比較の公正さと初版の範囲

初版は読み取り専用課題に限定し、空でないwriteScopeをコンパイル時に拒否する。すべての方式に同じtaskを渡す。役割プロンプトは方式に応じて異なるため、これはモデルそのものだけでなく運用方式の比較である。各方式の回答は他方式のプロンプトに含めないが、共有ファイルを読むことまで隔離する仕組みではない。

実験では更新されるSlackやWebを直接読ませず、許可された資料を先に固定する。回答の一時保存場所、プロファイルから見える情報、ツール、依存関係も揃える。実装課題は方式ごとの独立したworktree・同一初期状態・副作用隔離が必要なため、初版では受け付けない。

順番による影響はorderを入れ替えた複数試行で調べる。試行の自動反復は初版に含めない。失敗結果や相談が発生しなかった結果も除外しない。ホスト例外・キャンセルは実験を中断し、通常のblocked/null/不正な回答はその方式の失敗として残して他方式を実行する。

## 結果と評価

完全な結果には入力・経路指定・各方式の全ノード結果・相談内容・呼び出し数が残る。ツールの短い表示はstatus、callsStarted、summaryのみ。完全な結果への参照を保存する。最終状態は`awaiting-evaluation`であり、子のdoneを品質合格とは扱わない。

各方式のmeasurementsは次の形式で出力する。ホスト情報を取得できない欄を0や推測値で埋めない。

| 欄 | 評価時に結び付ける証拠 |
|---|---|
| effectiveModel | 子Sessionの要求・実効モデル情報。相談方式は全呼び出し分 |
| inputTokens / outputTokens | 全子呼び出しの利用量。引き継ぎ入力も含む |
| cost | 実際の課金情報と通貨・料金条件。取得不能ならnull |
| elapsedMs | 方式開始から終了までの実測時間 |
| independentAcceptance | 固定ルーブリックまたは決定的テストによる合否と証拠 |

現時点では数値欄はnull、independentAcceptanceはpendingであり、自動のテレメトリ収集・採点は未実装。後から採点する際は元の実行結果を保持し、run/子Sessionとの対応、判定基準、証拠への参照を持つ別の評価記録を作る。現在のworkflowフックだけではこれらの実測値は得られない。

採用判断は品質を先に判定し、合格した結果の総費用・時間・人の修正量を比較する。失敗率、相談率、相談による改善も併記する。初回構築費用と実験を起動する親Sessionの費用は方式の実行費用と区別して記録する。

## 保証の限界

固定コードが保証するのは分岐、順序、相談上限、方式間のプロンプト分離、全体最大5呼び出しの事前検証である。子のツール呼び出し回数、金額、時間、再帰委譲禁止、ファイル権限、実効モデルの一致をこのrunnerだけで強制するものではない。モデルへの指示はsandboxではない。必要なホスト制御を確認できるまで無人の費用制限付き運用とは呼ばない。

## 検証

`node --test tests/comparison.test.mjs`はモデルを呼ばず、相談なし・相談あり・相談失敗・相談上限・方式の失敗独立性・ホスト中断・入力制約・経路指定・回答非共有を検証する。実モデルでの品質、料金、実効モデル、ネイティブworkflow統合は別途確認する。

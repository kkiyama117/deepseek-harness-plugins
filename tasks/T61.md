### Design (decided by the lead after dsh-manager's review)

The Core separation check reads the live Core checkout, so it must not run for a root change that has nothing to do with Core: an unrelated uncommitted change in Core would then fail, for example, a `.gitignore` pull request. `bin/gate.py` keeps its per-directory keys; no per-file mapping is added. Instead the one `.` check looks at what changed: it runs the Core separation check only when `core-exceptions.json` differs from the merge base with `origin/main`, and otherwise prints one line and exits 0. Every other root non-Markdown file is then seen only by `git diff --check` (whitespace); `check-layout-links.py` reads only Markdown. That is intended: most of those files are dependency or build files that only the lead or dsh-manager changes, and a content check for them is out of this card's scope. `SOURCE-OWNERSHIP.md` does not trigger the check: it is Markdown, carries no checked value (the base and hash live in `core-exceptions.json`), and the document checks cover it.

### Rules

1. Add exactly one key, `.`, to the top-level object of `bin/gate-checks.json`, with exactly one check object: `"cwd": "."`, `"env": {"DSH_UPSTREAM_ROOT": "/data/softwares/deepseek-harness"}`, and this `run` (one line; JSON-escape the double quotes):

   ```sh
   b=$(git merge-base origin/main HEAD) || exit 1; if git diff --quiet "$b" -- core-exceptions.json; then echo "core-exceptions.json unchanged since the merge base; Core separation check skipped"; else python3 bin/check-core-separation.py --core "$DSH_UPSTREAM_ROOT"; fi
   ```

2. Keep the keys in byte order (the order `sorted()` gives in Python), so `.` becomes the first key. Keep the file's format: two-space indentation, `"cwd"` before `"run"` before `"env"`, a final newline. Change no other key.
3. In `bin/test_gate.py`, `RepositoryChecksTest.test_repository_checks_file_is_valid`: add `'.'` to the expected key list, and add a `'.'` row to the `rows` dict with the exact `run` string of rule 1 and the `env` `{'DSH_UPSTREAM_ROOT': '/data/softwares/deepseek-harness'}` (the existing loop already expects `cwd` equal to the key, which is `.`). Change nothing else in that file.
4. Do not change any other file. The bare `python3` call follows the gate's convention ([#43](https://github.com/kkiyama117/deepseek-harness-plugins/issues/43)); do not use `uv run`. Run the gate with `DSH_UPSTREAM_ROOT` unset or set to `/data/softwares/deepseek-harness`.
5. The check writes nothing. It reads this worktree's Git metadata and `core-exceptions.json`, and the Core checkout through `git`. It follows the live Core on purpose. On this branch `core-exceptions.json` differs from the merge base with `origin/main`, so the Core check runs. If the run exits non-zero for any reason (an `issues` entry such as a diff outside the exception, a different exception patch, any untracked file that Git does not ignore, or a base that is not an ancestor; or an error before any JSON, such as a failing `git merge-base`), do not change the command or the policy: stop, and put the full output of the `.` check in your report.
6. Known limits, leave as is: `SOURCE-OWNERSHIP.md` keeps its manual `uv run --no-project` command; the gate uses `python3` per #43, and this card does not edit that document. The skip branch is not exercised by a test in this card; the lead ran the `run` string on `issue/72-rc1-upgrade`, where `core-exceptions.json` matches the base, and saw the skip line with exit 0. And the check computes its own base from `origin/main`, so `python3 bin/gate.py --base <other ref>` still compares `core-exceptions.json` with `origin/main`'s merge base.
7. This card adds a configuration entry, not guard code, so it has no `Must fail without:` line. The gate run is not hermetic by design: it depends on the live Core.
